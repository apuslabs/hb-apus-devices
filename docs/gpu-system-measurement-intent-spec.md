# GPU System Measurement Intent and Specification

Status: Implemented v1 / local and remote probe validated
Owner: Apus HyperBEAM Devices
Scope: External HyperBEAM Device Forge repository only

Compatibility pin: official HyperBEAM `edge` commit
`2c03978a3d201444bf7aada3eb35809153e41ef3`.

## 1. Intent

Add a consumer-GPU trust layer without modifying HyperBEAM core.

The system must treat a GPU as host-observed hardware state, not as an
independent hardware root of trust. The existing TPM, SNP, or Android-backed
measurement chain remains the trust anchor. GPU inventory and selected runtime
facts are collected by external devices and composed with the existing
inference and agent devices.

The resulting claim is deliberately bounded:

> A node measured by the configured host measurement chain reported a
> canonical GPU inventory and produced a signed observation/receipt associated
> with that node and workload.

The system must not claim that a consumer GPU independently attested itself or
that an inference result is mathematically proven correct.

## 2. Non-goals

- No changes to HyperBEAM core modules or preloaded core devices.
- No NVIDIA GPU Attestation, NVAT, GPU certificate, or GPU hardware root of trust.
- No Zone admission policy in v1.
- No replacement of the existing `inference@1.0`, `sev_gpu@1.0`, or `agent@1.0`
  default behavior.
- No trust score generated by the system report itself. Facts and provenance
  are reported; policy remains with the caller.
- No claim that PCIe/sysfs/NVML data cannot be spoofed by a compromised host.

## 3. Existing compatibility contract

The external repository currently publishes:

| Device | Existing role | Compatibility requirement |
| --- | --- | --- |
| `inference@1.0` | OpenAI-compatible relay to a local or remote backend | Existing exports and request/response shapes remain valid |
| `sev_gpu@1.0` | Optional NVIDIA attestation prototype | Remains available and unchanged in the default path; this spec does not call it |
| `agent@1.0` | ReAct loop that calls `inference@1.0` | Default route remains `inference@1.0`; measured routing is opt-in |

The external repository must continue to package through Forge as ordinary
third-party devices. The runtime must consume signed generated `_hb_device_*`
archives, not raw source modules.

## 4. Device set

### 4.1 `gpu_inventory@1.0`

This is the primary new device. It is a read-only observation device and does
not make policy decisions.

Exports:

- `info`
- `report`
- `digest`

`report` returns an AO-Core response with this body shape:

```erlang
#{
    <<"type">> => <<"apus-gpu-inventory">>,
    <<"version">> => <<"1.0">>,
    <<"collected-at-unix">> => UnixSeconds,
    <<"provenance">> => #{
        <<"class">> => <<"host-observed">>,
        <<"sources">> => [<<"sysfs">>, <<"drm">>, <<"nvml">>]
    },
    <<"supported">> => true | false,
    <<"devices">> => [Gpu],
    <<"topology">> => Topology,
    <<"inventory-digest">> => Digest,
    <<"errors">> => Errors
}
```

The first implementation must work without a native dependency. It should use
read-only Linux surfaces such as `/sys/bus/pci/devices`, `/sys/class/drm`,
`/sys/kernel/iommu_groups`, and module metadata. An optional NVML helper may
provide additional fields, but its absence must not make the device pretend
that inventory is hardware-attested.

Each GPU record may include:

```erlang
#{
    <<"pci-bdf">> => ...,
    <<"vendor-id">> => ...,
    <<"device-id">> => ...,
    <<"subsystem-vendor-id">> => ...,
    <<"subsystem-device-id">> => ...,
    <<"revision">> => ...,
    <<"drm-card">> => ...,
    <<"driver">> => ...,
    <<"driver-version">> => ...,
    <<"firmware-version">> => ...,
    <<"gpu-uuid">> => ...,
    <<"vram-bytes">> => ...,
    <<"iommu-group">> => ...,
    <<"pcie-link">> => #{
        <<"speed">> => ...,
        <<"width">> => ...
    },
    <<"mig">> => ...
}
```

The digest input must be canonical, sorted, and exclude volatile fields. The
default v1 digest input includes device identity, driver/firmware identity,
IOMMU membership, PCIe link facts, and topology. It excludes temperature,
power, utilization, memory usage, and process lists.

### 4.2 `inference_measurement@1.0`

This is a composition adapter, not a replacement for HyperBEAM or PermawebOS
measurement code.

Exports:

- `info`
- `boot`
- `fresh`
- `verify`
- `snapshot`

The adapter defaults to `auto` and also accepts two explicit modes:

`hook-body` mode, when `~measurement@1.0` is available:

1. Resolve `~gpu_inventory@1.0/report`.
2. Hash the caller's nonce and the inventory digest into a measurement nonce.
3. Call `~measurement@1.0/boot` or `fresh` through its public interface.
4. Preserve the upstream subject: `~system@1.0/all` plus `~meta@1.0/info`.
5. Return the original measurement envelope plus composition metadata and
   available CPU/GPU evidence.

The retained `hook-body` option name selects this integration; it does not
replace the upstream subject. Fresh measurements bind the request and GPU
inventory through the nonce. Cached boot measurements retain the upstream
backend's lifecycle and do not establish a new request binding.

`observation-only` mode, when `~measurement@1.0` is unavailable:

- Return the node-signed observation envelope and GPU digest.
- Set `provenance.class` to `host-observed`.
- Set `measurement-integration` to `false`.
- Never label the result `tpm-bound`, `snp-bound`, or `hardware-attested`.

The adapter must fail closed on integration metadata: if the base measurement
cannot be resolved or verified, it may return an observation-only result but
must not silently upgrade its trust label.

Example composition metadata:

```erlang
#{
    <<"type">> => <<"apus-gpu-system-measurement">>,
    <<"version">> => <<"1.0">>,
    <<"measurement-integration">> => true,
    <<"integration-mode">> => <<"measurement-nonce">>,
    <<"base-measurement-id">> => ...,
    <<"gpu-inventory-digest">> => ...,
    <<"nonce-binding">> => ...,
    <<"subject-id">> => ...,
    <<"provenance-class">> => <<"host-measured-subject">>
}
```

### 4.3 `inference_receipt@1.0`

This is a decorator around the existing `inference@1.0` device.

Exports:

- `info`
- `completions`
- `chat`
- `models`
- `health`
- `v1`
- `verify-hashpath`
- `publish`

`models` and `health` delegate without a receipt. `completions` and `chat`
delegate to `inference@1.0`, then attach an observation or receipt to the
response without changing the underlying inference request semantics.

For non-streaming responses, the receipt body is:

```erlang
#{
    <<"type">> => <<"apus-inference-receipt">>,
    <<"version">> => <<"1.0">>,
    <<"request-id">> => ...,
    <<"request-digest">> => ...,
    <<"response-digest">> => ...,
    <<"model">> => ...,
    <<"workload-manifest-id">> => ...,
    <<"gpu-inventory-digest">> => ...,
    <<"measurement-id">> => ...,
    <<"issued-at-unix">> => ...,
    <<"sequence">> => ...,
    <<"provenance-class">> => <<"host-observed">>,
    <<"signature">> => ...
}
```

The receipt is a signed observation of the node-side request/response
transcript. It is not a proof that the GPU produced the response.

Streaming is not supported by receipt v1. The decorator must either reject
`stream=true` with an explicit error or require an explicit
`receipt-mode=observation-only` path that makes no completeness claim. The
existing `inference@1.0` streaming behavior remains unchanged.

### 4.4 `agent@1.0` integration

The existing default remains unchanged. The agent may gain one optional
external-device setting:

```text
agent-inference-device = inference@1.0
```

Setting it to `inference_receipt@1.0` routes LLM calls through the decorator.
The default `agent@1.0` path continues to call `inference@1.0`, so existing
deployments and Lua callers do not change behavior.

If adding this option is deferred, trusted local configuration may inject the
existing `agent-llm-fun`; the production-friendly contract is the explicit
device name because functions cannot be carried safely through ordinary JSON
messages.

## 5. Trust classes

The devices must use explicit provenance labels:

| Class | Meaning |
| --- | --- |
| `host-observed` | Read-only host/kernel/NVML observation; spoofable by a compromised host |
| `host-measured-subject` | GPU inventory was included in a subject consumed by the existing TPM/SNP/Android measurement chain |
| `runtime-observed` | Volatile state such as utilization or temperature; signed by the node but not boot-bound |
| `receipt-observed` | Request/response digest signed by the node-side device |

The implementation must never emit `gpu-attested` or equivalent language.

## 6. Static versus runtime GPU data

Boot-bound inventory is intentionally static:

- PCI identity and BDF;
- GPU UUID when available;
- driver and firmware identity;
- IOMMU group;
- PCIe link facts;
- MIG/topology configuration.

Runtime snapshots may include:

- temperature;
- power;
- utilization;
- memory usage;
- active process count.

Runtime snapshots are separate messages. They must not be inserted into the
cached boot subject unless the caller explicitly requests a new measurement
subject and the selected host backend supports that lifecycle. The existing TPM
backend binds the measurement body to its PCR/AK state; silently changing the
body for every fresh observation would invalidate that binding.

## 7. Composition with current devices

The composition graph is:

```text
agent@1.0
    -> inference_receipt@1.0 (opt-in)
        -> inference@1.0
            -> relay@1.0 -> configured inference backend
        -> gpu_inventory@1.0
        -> inference_measurement@1.0
            -> ~measurement@1.0 when available
            -> sev_gpu@1.0 for optional NVIDIA evidence
```

`gpu_inventory@1.0` only collects ordinary host facts. The measurement adapter
separately requests optional NVIDIA evidence through `sev_gpu@1.0`; absent
hardware attestation does not turn the inventory into a failure.

The decorator must preserve the existing response modes:

- direct HTTP response remains an HTTP-shaped response;
- AO scheduled message remains `{data, action}` shaped;
- only the response body/data gets the optional receipt field.

## 8. Forge and packaging requirements

All new devices live in the external repository as normal Forge roots:

```text
src/dev_gpu_inventory.erl
src/dev_gpu_inventory_*.erl
src/dev_inference_measurement.erl
src/dev_inference_measurement_*.erl
src/dev_inference_receipt.erl
src/dev_inference_receipt_*.erl
```

No HyperBEAM core source is changed. Inventory works without native code;
the optional SNP backend requires `make setup-measurement` on Linux before
packaging. Pinned upstream sources are under `vendor/permaweb-os`.

Forge requirements:

- pin the `hb` dependency and Forge plugin to one exact compatible commit;
- package with `rebar3 device package`;
- validate with `rebar3 device verify`;
- run device tests with `rebar3 device test`;
- run `rebar3 eunit-all` before publishing;
- publish signed specification and implementation messages;
- record spec IDs, implementation IDs, and signer in the release metadata.

The repository pins the same HyperBEAM commit for the `hb` dependency and Forge
plugin. HyperBEAM core remains unmodified; the external package is loaded as
ordinary signed Device Forge archives.

## 9. Required tests

### GPU inventory

- fixture-based sysfs report is deterministic;
- device ordering does not change the digest;
- volatile fields do not change the static inventory digest;
- missing NVIDIA/NVML support returns explicit `supported=false`, not a fake
  successful report;
- malformed sysfs values are represented as unavailable fields;
- no API keys, bearer tokens, or private material appear in the report.

### Measurement adapter

- integration preserves the upstream system/node subject;
- changing the request or static GPU inventory changes the fresh nonce binding;
- base measurement failure downgrades to observation-only or returns an explicit
  error; it never claims host-measured-subject;
- plain HyperBEAM without `~measurement@1.0` still produces a valid observation
  response;
- cached boot behavior is preserved.

### Inference receipt

- request and response digests are stable under canonical encoding;
- changing response bytes invalidates the receipt digest;
- the receipt references the GPU inventory digest and measurement ID used for
  the call;
- AO scheduled-message and direct HTTP response shapes remain compatible;
- streaming is rejected or explicitly downgraded, never silently claimed as a
  complete receipt;
- existing `inference@1.0` and default `agent@1.0` tests pass unchanged.

## 11. Confirmed decisions

These decisions are part of the v1 contract:

1. Inventory is generic PCI display/compute discovery with NVIDIA enrichment
   through a fixed `nvidia-smi` query when available. NVIDIA is not the only
   supported vendor, and absence of NVIDIA tooling is a valid result.
2. v1 exposes both a static inventory report/digest and a separate lower-trust
   runtime snapshot. Volatile values never enter the static digest.
3. `inference_receipt@1.0` retains the inference output and adds the receipt
   to the JSON body as well as sibling AO-Core metadata. Streaming is rejected
   by the decorator.
4. `agent@1.0` keeps `inference@1.0` by default. `agent-inference-device` is
   the explicit opt-in for `inference_receipt@1.0`.
5. `sev_gpu@1.0` supplies optional GPU attestation to the measurement adapter;
   the inventory device remains independent of TEE.
6. When `measurement@1.0` is absent, the adapter is observation-only. When it
   is present, the adapter retains the standard system/node subject and binds
   fresh request and inventory facts through the nonce. CPU evidence retains
   the upstream verifier result separately from successful collection.

## 12. Validation evidence and boundaries

The Device Forge tests cover deterministic inventory digests, exclusion of
volatile fields, NVIDIA CSV parsing, measurement mode selection, receipt
request digests, and streaming truth parsing. The six APUS roots and three
upstream roots package and load under the pinned HyperBEAM commit.

On a macOS host without NVIDIA, a local Forge node reports
`supported=false`, `provenance.class=host-observed`, and
`measurement-integration=false`. A remote Windows machine with an RTX 4090 was
queried separately through `ssh pc-win`; that output is fixture/observation
evidence only and is never presented as the local node's measured hardware.
The checked-in scripts/pc-win-inference-gpu-probe.ps1 now performs the same
probe from that Windows host: it collects nvidia-smi inventory/runtime fields,
calls the published inference@1.0 endpoint, and emits request, response, and
joint digests. This remains host-observed evidence rather than local-node
hardware measurement.

The existing real-API `dev_agent` integration test remains environment
dependent and currently fails because its pre-existing OpenRouter API key is
expired. That failure is not used as evidence for GPU or receipt behavior.

Deferred policy questions include Zone/verifier admission and any future
operator scoring. They are intentionally outside this device contract.
